## Problem Statement

The internal SEO agency workflow is spread across the product, third-party/free tools, spreadsheets, and manually assembled documents. Senior SEO analysts spend too much time collecting data, reconciling it, explaining what changed, and formatting client-facing reports. The current app has many useful modules, but the flow feels inconsistent and the team does not yet trust it for core delivery work.

The product should become the agency's operating system: one client and project context, one source-backed data workspace, one clear view of what changed and what is wrong, and one reusable path from evidence to assigned action to shareable report.

## Demand Evidence

- The team already uses the humanizer and blog-related workflows because they work as expected. This proves there is some existing pull for focused workflows.
- The strongest repeated pain is senior SEO analyst time spent gathering data from several tools and rebuilding manual documents and sheets.
- The team explicitly wants accurate, trustworthy outputs and a more uniform UI/UX. Trust is a delivery requirement, not a visual preference.
- There is no measured time baseline or direct observation of an analyst using the current product yet. That evidence gap is part of the first assignment.

## Status Quo

For client work, analysts move between SEO data sources and the product, collect results, reconcile values, and manually assemble a report or spreadsheet. The product may contain the underlying capabilities, but it does not yet present a dependable end-to-end workflow. Analysts therefore keep external tools and manual documents as the trusted fallback.

The status quo costs senior time, creates repeated formatting work, makes metric discrepancies hard to explain, and increases the risk that a client report contains stale, estimated, or poorly sourced data.

## Target User & Narrowest Wedge

The primary user is the senior SEO analyst responsible for turning technical, search, content, and analytics data into a client deliverable. The secondary users are account managers and agency owners who need a consistent view of client health, completed work, risks, and next actions.

The selected direction is a full SEO agency operating system. The first proving slice is still narrow: select a client and project, confirm data-source health, review the latest evidence, generate a report draft, inspect the source behind each claim, convert findings into tasks, and share/export the result.

## Constraints

- This is an internal agency product with real users but not yet enough trust for core delivery.
- Accuracy and explainability are more important than adding more modules.
- Existing working capabilities, especially keyword research, on-page SEO, and technical SEO, should be preserved and improved rather than discarded.
- Every important metric must show its source, collection time, freshness, coverage, and whether it is measured, estimated, cached, or unavailable.
- Third-party and open-source tools may remain part of the data pipeline, but they must not be hidden behind unsupported claims of precision.
- The product should stay free for the agency and reuse the existing Node.js, Fastify, PostgreSQL, and EJS foundation where practical.
- The UI needs a consistent information hierarchy, navigation model, terminology, loading states, empty states, error recovery, and responsive behavior.

## Premises

1. The highest-value outcome is reducing analyst time from raw data collection to a verified client-ready report and action plan.
2. Trust requires metric provenance, freshness, coverage, calculation visibility, and honest failure states; UI consistency alone is insufficient.
3. The current SEO modules are valuable building blocks that should feed one agency workflow rather than remain isolated destinations.
4. The product should distinguish source-backed facts, derived scores, estimates, and AI-generated interpretation throughout the UI and report.
5. Humanizer and blog workflows need improvement, but the first system-level bet is reliable agency delivery: evidence, explanation, action, and report.

## Approaches Considered

### Approach A: Report-first command center

Reorganize the current dashboard around client, project, report, and actions while keeping most existing data paths intact. This ships visible UX improvements quickly, but risks polishing untrusted data without fixing the evidence model underneath.

### Approach B: Full SEO agency operating system

Unify client onboarding, project health, data sync, analysis, recommendations, tasks, approvals, branded reports, sharing, and history into one internal workflow. This is the selected direction because the agency needs one operating surface, not another isolated SEO utility. Delivery should be staged around the report-and-action proving slice so the team sees value before the entire system is complete.

### Approach C: Evidence ledger and report compiler

Add a source-backed evidence layer where every important result carries source, timestamp, freshness, confidence, calculation, and error state, then compile reports and tasks from that evidence. This is the strongest accuracy foundation and should be adopted as a core architectural pattern inside Approach B, even though it is not the whole product by itself.

## Recommended Approach

Build Approach B as the product direction, using the evidence-ledger ideas from Approach C as a non-negotiable trust layer.

The system should have a clear spine:

```text
Agency -> Client -> Project -> Data sources -> Evidence -> Insight -> Task -> Report -> Share/history
```

The redesigned experience should open in the context of a client or project, not a generic feature list. The home view should answer three questions immediately: what changed, what needs attention, and what should happen next. Reports should be assembled from the same evidence users inspect in the workspace. Every number should be traceable, and every recommendation should distinguish observed data from analysis or AI interpretation.

The product should be staged in this order:

1. Establish the client/project workspace and consistent navigation.
2. Normalize data-source status, freshness, provenance, and error states.
3. Build the report workspace with reusable sections, evidence drill-down, narrative editing, action generation, export, and share history.
4. Connect audit, keyword, rank, GSC, GA4, PageSpeed, content, task, and competitor workflows into the same project context.
5. Improve the humanizer and blog workflow after the agency delivery spine is trusted.

## Success Criteria

- A senior analyst can select a client/project and produce a reviewable report draft without rebuilding the same data in a spreadsheet.
- Every report metric has a visible source, last-updated timestamp, coverage indicator, and status such as measured, estimated, cached, or unavailable.
- Analysts can open a report claim and inspect the supporting evidence and calculation without leaving the product.
- Every high-priority finding can become a task with owner, priority, status, source evidence, and a clear next action.
- Reports can be generated from reusable templates, edited by an analyst, exported, and reopened with their history intact.
- A baseline is measured with one real analyst workflow, then the first release reduces manual reporting time by at least 50% without increasing data corrections.
- Human reviewers can identify why a number changed and whether a recommendation is based on source data, a rule, or AI interpretation.

No separate package or public marketplace distribution is required for this internal phase.

- Reliable background sync status and job history for providers that can be slow or rate-limited.

- An observed analyst workflow and baseline timing before claiming that the redesign saves time.

### Review sections

#### 1. Architecture

```text
                    ┌───────────────┐
                    │ Client/Project│
                    │ workspace     │
                    └───────┬───────┘
                            │ context + permissions
      ┌──────────────┬──────┴───────┬──────────────┐
      ▼              ▼              ▼              ▼
   GSC/GA4        SERP/keywords   Crawl/audits   PageSpeed
   adapters      existing flows  orchestrator   existing flow
      └──────────────┴──────┬───────┴──────────────┘
                             ▼
                  ┌────────────────────┐
                  │ Evidence/provenance│
                  │ normalizer + ledger │
                  └───────┬────────────┘
                          ├──────────────► Source health/run history
                          ▼
                 ┌────────────────────┐
                 │ Insight/finding     │
                 │ rule + AI label     │
                 └────────┬───────────┘
                          ├──────────────► Tasks with evidence links
                          ▼
                 ┌────────────────────┐
                 │ Report compiler     │
                 │ snapshot + history  │
                 └────────┬───────────┘
                          ▼
                 Review → export/share → reopen/audit
```

The new coupling is intentional: reports, tasks, dashboard cards, and source health must read the same normalized evidence instead of independently recomputing values. Provider adapters remain isolated behind existing services.

Data-flow shadow paths:

```text
Provider response → validate shape → normalize → persist evidence → derive claim → render
       nil/error          reject + unavailable   no fake zero       stale label       drilldown
       empty              empty coverage        partial snapshot   warning           correction path
```

State machine for a report snapshot:

```text
DRAFT ──compile──▶ READY_FOR_REVIEW ──approve/export──▶ PUBLISHED
  │                     │                                  │
  └─invalid/partial────► NEEDS_ATTENTION ◄──new sync──────┘
READY_FOR_REVIEW ──edit──▶ DRAFT
PUBLISHED ──never mutates; new run creates a new snapshot──▶ DRAFT
```

Invalid transitions are prevented by server-side status checks and immutable published snapshots. A provider failure creates an unavailable/partial evidence status; it never becomes a zero-valued success.

Scaling: the first pressure point is provider rate limits and crawl duration, then report compilation over large projects. Use background jobs, bounded page/keyword batches, indexed project/agency keys, and snapshot reads. At 100x volume, a single PostgreSQL queue/worker process becomes the main bottleneck; isolate provider queues and add retention/partitioning before that point.

Single points of failure: PostgreSQL, provider credentials/APIs, the worker process, and report export. Each must surface health and recovery state in the product.

#### 2. Error and rescue map

| Codepath | Failure | Required rescue | User sees |
|---|---|---|---|
| Provider sync | timeout/429 | bounded retry with backoff; record failed run | “Sync delayed” + last successful time |
| Provider sync | malformed/empty response | schema validation; store unavailable/partial evidence | explicit coverage warning |
| Evidence normalization | unknown metric/unit | reject claim; log context; keep raw run | “Not reportable” instead of guessed value |
| DB snapshot write | conflict/connection exhaustion | transaction retry where safe; otherwise fail run visibly | retry action + run ID |
| Report compilation | missing source or stale source | compile with blocked sections, not silent omission | section-level warning |
| Export/share | permission/file/render failure | re-raise with report ID; clean retry | export failed with retry |
| Task creation | duplicate submission | idempotency key or unique finding/report key | existing task returned |
| AI summary (later) | empty/refusal/invalid JSON | schema-validate; mark AI unavailable; never invent facts | source-backed report remains usable |

Catch-all handlers must add request, agency, client/project, codepath, and run identifiers to structured logs. “Log and continue” is not acceptable when a claim could be wrong.

#### 3. Security and threat model

The highest-risk current pattern is the permissive agency condition used in several queries: `(agency_id = $1 OR agency_id IS NULL OR $1 IS NULL)`. This may be useful for legacy single-tenant data, but it is unsafe as a default for a trusted agency product. P1: make tenant scope explicit, reject missing agency context for agency data, and add object-level authorization tests for every report, evidence, task, and source endpoint.

Other findings:

| Threat | Likelihood | Impact | Mitigation |
|---|---:|---:|---|
| Client/project/report IDOR | Medium | High | central access guard + cross-agency integration tests |
| Provider credential leakage in logs/reports | Medium | High | redact tokens, encrypt at rest where supported, audit access |
| HTML/script injection through report content | Medium | High | escape EJS/UI output; sanitize rich text; CSP review |
| Prompt injection from crawled/page content | Medium | High | treat page text as untrusted; AI never controls actions or source facts |
| Export/share link overexposure | Medium | High | expiring signed links, permission check, revoke/audit events |
| SQL/filter injection | Low | High | parameterized queries and allowlisted sort/filter fields |

#### 4. Data and interaction edge cases

```text
User selects project
  ├─ missing project       → block and return to project picker
  ├─ project has no sources → show setup checklist, no fake dashboard score
  ├─ source is stale        → render value with stale badge + last success
  ├─ source partially fails → show coverage denominator and affected sections
  └─ source is fresh        → persist evidence → derive claims → compile draft
```

Required interaction handling: disable duplicate sync/report actions while in flight; preserve job state when navigating away; show empty states for new projects; paginate or virtualize large tables; make retry safe and idempotent; allow a report to be saved when only some sources succeed, with blocked sections clearly marked; never turn a provider error into an empty success.

#### 5. Code quality

The main quality risk is duplicated metric shaping across `public/js/app.js`, route handlers, report services, and individual module scripts. The first implementation should create one server-side contract and a thin client renderer, rather than adding more page-specific formatting. Avoid a large new framework or rewrite: add small modules for evidence normalization, report compilation, and access policy, then migrate one report slice.

#### 6. Test review

```text
UX: project workspace → source health → evidence drilldown → report draft → task → export/share
Data: provider run → normalized evidence → claim → snapshot → rendered report
Code: validation, freshness, partial coverage, permissions, idempotent task creation
Async: GSC/GA4/SERP/crawl/PageSpeed run status, retry, timeout, duplicate run
External: provider timeout, 429, malformed JSON, empty response, expired credential
Rescue: unavailable/partial/stale states and report-level blocked sections
```

Minimum confidence suite: unit tests for provenance normalization and status transitions; integration tests for tenant scope and report compilation from fixtures; system tests for the full report flow; contract tests for each provider adapter. Hostile QA should try cross-agency IDs, stale runs, empty arrays, duplicate clicks, and a report whose only source fails. Chaos test: terminate a worker during compilation and verify the report remains draft/partial and can resume without duplicate tasks.

#### 7. Performance

Do not compile a report by issuing one provider call per card. Fetch bounded source snapshots once, normalize once, and build claims from stored evidence. Add indexes for agency/client/project/report snapshot/run lookups. Keep crawls and exports asynchronous, cap batch sizes, and expose progress. Cache only immutable evidence/report snapshots; never cache a value without its source timestamp.

#### 8. Observability

Every source run and report compile should emit structured start/success/failure events with `agencyId`, `clientId`, `projectId`, `runId`, source, row/page counts, duration, freshness, and error class. Add metrics for sync success rate, stale-source rate, partial-report rate, report compile duration, export failure rate, correction rate, and manual spreadsheet rebuilds. The first operational panel should answer: “Which client reports are blocked or based on stale data right now?”

#### 9. Deployment and rollback

Use additive migrations for evidence/run/snapshot tables. Deploy schema first, then code that writes new records, then enable the new workspace behind a project/agency flag. Backfill only from known source records; do not fabricate historical provenance. Verify a fixture project, one fresh sync, one failed sync, one partial report, export, and cross-agency denial after deploy. Roll back by disabling the flag and reverting code; retain additive tables until the new path is proven.

#### 10. Long-term trajectory

Reversibility: 4/5 if the evidence contract is additive and published snapshots are immutable. The platform opportunity is real: once every module emits the same evidence shape, new SEO checks, content workflows, and AI recommendations can consume it without inventing new report logic. The main debt risks are unclear metric ownership, unbounded provider-specific exceptions, and skipping the analyst baseline.

#### 11. Design and UX review

The current information architecture is feature-first. The redesigned hierarchy should be:

```text
Agency
 └─ Client
     └─ Project workspace
         ├─ Overview: what needs attention now
         ├─ Data health: sources, freshness, coverage, failed runs
         ├─ Work: findings, tasks, owners, priorities
         ├─ Reports: draft, review, export/share, history
         └─ Tools: keyword, on-page, technical, content, humanizer
```

User flow:

```text
Pick client/project → see “what changed” → inspect source health
       ↓                    ↓                    ↓
   empty/setup         finding details       retry/refresh
       ↓                    ↓                    ↓
  connect sources → evidence drawer → create task → report draft
                                               ↓
                                  review → export/share → history
```

State coverage must exist for every workspace card: loading, empty, error, partial, stale, success, and permission denied. The emotional arc should move from “where do I start?” to “I know what changed,” then “I can prove this number,” then “I know what to do next,” and finally “the client-ready artifact is already here.”

Anti-slop rules: no dashboard wall of rounded cards, no unexplained health score, no decorative gradients, no unlabeled AI copy, and no “success” state when data is estimated or stale. Use a restrained Stitch design system, one primary action per view, consistent table/filter/empty/error patterns, keyboard-visible focus, WCAG AA contrast, and responsive layouts that preserve the project context and report actions on small screens.

### NOT in scope

- Rebuilding working keyword, on-page, and technical algorithms without evidence of incorrect output.
- Replacing the SERP API or every open-source provider in the first slice.
- A full humanizer/blog redesign; those flows are useful but need their own quality evaluation.
- Social, backlink, and broad competitor intelligence consolidation.
- Realtime collaboration and marketplace/public SaaS packaging.
- Claiming “free equals every paid product” as a contractual promise.

## Stitch Design Review

Stitch project: `11475557801860041328`

Reference screens: `.stitch/designs/project-overview/`, `.stitch/designs/report-workspace/`, `.stitch/designs/report-workspace-mobile/`

### Design scope and existing leverage

Initial design completeness was 7/10: the product hierarchy and states were described, but the existing feature-first shell, visual language, and responsive behavior were not concrete enough. After the Stitch references and `DESIGN.md`, the first implementation slice is 9/10: it has a visual north star, layout hierarchy, explicit states, a desktop/mobile pattern, and component rules. A 10/10 requires rendered implementation QA against real API states and keyboard/zoom testing.

Existing leverage to preserve: the server-rendered EJS shell in `views/index.ejs`, SPA navigation in `public/js/app.js`, existing report/task pages and styles, and the current specialized module styles. The first UI change should introduce shared shell/state primitives and migrate one project/report flow; it should not duplicate a second application shell for every tool.

### Pass 1 — information architecture (9/10)

Constraint: if the first viewport can show only three things, show **selected project context**, **what needs attention**, and **whether the data is trustworthy enough to report**. The order is context → change → proof → action → delivery. Tool pages remain reachable under the project but do not compete with project outcomes.

### Pass 3 — user journey and emotional arc (9/10)

| Step | User does | User should feel | Design support |
|---|---|---|---|
| 1 | Selects client/project | Oriented | persistent context and last-run timestamp |
| 2 | Scans what changed | In control | short change summary with source/freshness |
| 3 | Checks source health | Safe to trust | explicit Fresh/Partial/Stale/Unavailable labels |
| 4 | Opens a claim | Able to verify | evidence drawer without leaving report |

The 5-second test is “which project and what is blocked?” The 5-minute test is “can I verify the important claims and assign work?” The longer-term test is “can I explain why last month’s report changed?”

### Pass 4 — AI slop and visual quality (8/10)

The references correctly avoid the generic SaaS hero, equal card grid, and decorative imagery. One failure was caught: Stitch generated invented sample metrics, dates, URLs, and client-like labels despite placeholder instructions. Those visuals are layout-only. Production templates must use real API values, `[not collected]`, or explicit unavailable states; no fixture-like sample numbers may ship in UI copy.

The generated theme also contains a default tertiary/cyan token. Ignore it unless a real semantic status requires it; the product palette stays paper, charcoal, moss, copper, green, ochre, and brick. Do not copy Stitch’s sample “Q4” report title or example URLs into production.

### Pass 5 — design-system alignment (9/10)

`DESIGN.md` is now the local source of truth and is attached to Stitch. Implement CSS variables for the Evidence Desk palette, Satoshi/Plus Jakarta Sans-compatible body styling, IBM Plex Mono data values, 240px rail, 1280px content maximum, 44px targets, and semantic status tokens. Use structural lines and open sections before panels. A later 10/10 pass requires checking the final rendered font availability and contrast in the actual deployment environment.

### Pass 6 — responsive and accessibility (9/10)

Desktop uses a persistent rail and open tables. Below 768px, the rail becomes a labeled drawer, tables become stacked evidence rows, and the evidence drawer becomes a full-screen sheet. Core report actions must never require horizontal scrolling. Use `nav`, `main`, and `aside` landmarks, visible 2px focus, associated labels, live progress regions, 44px targets, reduced-motion behavior, and non-color status text. Validate at 375px, 768px, 1024px, and 1440px plus 200% zoom.

## Engineering Review

### Scope and leverage check

The plan touches more than eight files and introduces more than two conceptual services, so it is a staged migration rather than one rewrite. The smallest proving slice is: tenant-safe project context, normalized evidence, source health, immutable report snapshot, finding-to-task link, and one migrated overview/report flow. Keyword, on-page, technical, humanizer, social, and competitor pages remain on their existing routes until their outputs are proven through the shared contract.

Runtime and test evidence: Node/CommonJS, Fastify v5, PostgreSQL, EJS, raw parameterized SQL, and Vitest. Existing tests are concentrated in `tests/unit/` (`rankedKeywordsService`, `domainUtils`, `searchVisibilityService`, `rankTracker`, `aiHelper`, `humanizerService`); there is no existing report-flow or tenant-scope integration suite.

### Verified architecture findings

- **[P1] (confidence: 9/10) `src/routes/reports.js:26-29` — report generation authenticates the session but passes no `agencyId` into `buildReport`; `src/services/reportService.js:71-73` then queries a client by ID without agency scope.** A report can therefore be built from a client identifier without the new trust boundary. Fix by passing an authorized project/client context and enforcing it inside the service, not only in the UI.
- **[P1] (confidence: 10/10) `src/routes/reports.js:43-48` and `src/routes/ga4.js:35-38` — report and GA4 queries explicitly allow `agency_id IS NULL`.** This is a legacy compatibility path, not an acceptable default for client delivery. Make legacy rows explicit migration candidates and require an agency context for trusted workspace/report paths.
- **[P1] (confidence: 9/10) `src/services/reportService.js:163-171`, `173-183`, `185-210`, `212-232` — several source queries use `.catch(() => ({ rows: [] }))`.** A provider/database failure becomes an empty success-looking report. Replace with typed source-run outcomes (`success`, `partial`, `stale`, `unavailable`) and keep the exception visible in the snapshot.
- **[P1] (confidence: 9/10) `src/services/reportService.js:239-241` — report compilation can call `safeRunPageSpeed(reportUrl)` live after the parallel query set.** This creates a slow, non-repeatable report and makes delivery dependent on an external request at compile time. Prefer stored PageSpeed evidence; if missing, mark the section unavailable or queue a run.
- **[P2] (confidence: 9/10) `src/services/auditOrchestrator.js:288-309` — `listAudits` and `getAudit` filter by project/audit ID only.** Any new report/evidence consumer must wrap these reads in project/agency authorization or they become an IDOR path.
- **[P2] (confidence: 8/10) `src/routes/ga4.js:198-210` — bulk sync iterates all selected clients in one request.** A slow provider or large agency can keep a request open and put pressure on the connection pool. Move bulk sync to a bounded background job and return a run ID.

### Target architecture and data flow

```text
HTTP route + session
  → central access policy (agency/client/project)
  → source adapter/run record
  → validated provider payload
  → evidence normalizer (typed status + provenance)
  → immutable snapshot transaction
  → report/finding/task reads
  → EJS/vanilla-JS state renderer

nil input       → 400/setup state; never “0”
empty response  → empty/coverage state; never success by omission
provider error  → failed run + unavailable section + retry
DB conflict     → transaction retry or visible blocked snapshot
stale evidence → labeled value + last success + refresh action
```

The report snapshot should be a read model built from evidence, not another independent provider aggregator. The evidence contract is the platform boundary; adapters can remain provider-specific.

### State and invariants

```text
SOURCE_RUN: queued → running → succeeded
                     ├→ partial
                     ├→ failed → retryable
                     └→ cancelled

REPORT: draft → ready_for_review → published
           └→ needs_attention
published ──new source run──▶ new draft (published snapshot never mutates)
```

Invariants: a published report references immutable evidence; a `succeeded` source run has validated payload and coverage; a `partial`/`failed` run cannot silently satisfy a report section; a task created from a finding preserves the evidence and snapshot IDs; every read and mutation is agency-scoped.

### Code quality findings

- **[P1] (confidence: 9/10) `src/services/reportService.js:72-73` — client mode is mixed with domain-only mode and uses the fallback label `'Your Website'`.** Domain-only research may be useful, but client reports must never silently switch identity or source scope. Split report workspace compilation from anonymous/domain preview, or require an explicit preview mode.
- **[P2] (confidence: 9/10) `src/services/reportService.js:34-65` — `buildPageSpeedFallback` derives a performance score from crawl load time.** This can be useful, but it is a derived estimate, not PageSpeed. The normalized contract must label it `estimated`, name the formula, and keep it separate from measured Core Web Vitals.
- **[P2] (confidence: 8/10) `src/routes/reports.js:30-32` — failures return `err.message` directly.** Convert internal errors to stable error codes/messages while logging full context. Do not expose provider credentials, SQL details, or stack traces.

### Performance findings

- **[P1] (confidence: 9/10) `src/services/reportService.js:90-233` — one report gather issues a large `Promise.all` across roughly a dozen queries, including up to 1,200 GSC rows, before derived assembly.** Compile from bounded source snapshots and paginate/aggregate at the query boundary; add report-specific timing and row-count metrics.
- **[P1] (confidence: 9/10) `src/services/reportService.js:239-241` — live PageSpeed makes p95/p99 report latency provider-dependent.** Store provider runs asynchronously and compile from the last known evidence.
- **[P2] (confidence: 8/10) `src/db/index.js:784-810` — many client/project indexes already exist, but new evidence/run/snapshot uniqueness and lookup indexes are not planned.** Add `(agency_id, project_id, collected_at)`, source-run status/time, and snapshot/report lookup indexes with `EXPLAIN` checks.

### Security and deployment

Deploy schema → write evidence/run records → read the new report path → enable per agency/project. Roll back by disabling the flag and reverting code; retain additive tables. Reject missing agency context for trusted paths. Encrypt/redact provider credentials and ensure report HTML escaping/sanitization before share/export.

### DX investigation and TTHW

The README is broad and useful, but the first-run path requires `npm install`, copying `.env`, filling API keys, manually creating PostgreSQL database `keyword_analyzer`, and then `npm run dev` (README lines 193-216). Current TTHW is approximately 25–45 minutes and depends on PostgreSQL plus valid provider keys. Target TTHW for maintainers is under 10 minutes using Docker/fixture mode, with a safe seeded project and no external API keys required to see the report workflow.

Magical moment: **“I can run the app locally, open a seeded project, and inspect a trustworthy report claim with evidence in under ten minutes.”** Delivery vehicle: `npm run dev:fixture` or equivalent documented seed mode, fixture source runs, and a “View evidence” path that works offline.

### Developer empathy narrative

“I cloned the repository because a report is blocked. I read a long feature list, then discover I need PostgreSQL, a `.env`, and several provider keys before I can see anything. When a sync fails, I may get a provider error or an empty-looking report, and I do not know whether the data is missing, stale, or actually zero. I need one safe local command, one seeded project, stable error codes, and a short map from route to service to source run.”
